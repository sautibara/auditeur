## App as a Component?

App should be a component (probably in a marker registry)

- App depends on the RegistryEvent listen message
  - Add some component bootstrapping functionality that allows adding a loaded component
- Resources depend on the App when they get handles
  - App handles should hold a dependency
- App depends on other resources when they have runners
  - This should be a removable dependency, so that unloading the resource doesn't unload the app
- Running resources depend on the App while they're running
  - This should be an unremovable dependency, so that unloading the app does unload the resource

This actually means that we could automate/de-magic resources. If we support components having methods that are run with the app as a dependent when they're added to the registry, this would work.

## Transient Dependencies

Quite a lot of App methods accept external trait objects. This could be an issue if a handle sends one of those trait objects to a message queue and then the app unloads the dependent before handling the message. Once the app attempts to handle the message, it would be using data from an unloaded component, which with auditeur plugin could lead to undefined behavior.

The only issue is that this situation is super super unlikely - it would require both the app being slow and a resource cancelling a future. So the solution to this should be cheap but correct.

A solution that could work would be to introduce a transient dependencies counter to each component, backed by an atomic. When a component sends a trait object to the app, it'll increment the counter. Once the app finishes with the object, drop ordering will automatically decrement the counter. And when a component is marked to be unloaded, the app first checks the counter. If it's zero, the app just unloads it like normal. If it's nonzero, the app doesn't unload it and instead adds it to a queue of components to unload, which is checked periodically.

## Unloading

When do things unload or get destroyed?

- Dependencies are annoying because they absolutely keep the dependency alive, but they also imply the liveness of the dependent
- But we can't wait until all of a dependents dependencies unload to unload the dependent, because some of the dependencies may be blocked behind an unload
- So unloading really has to happen in two steps: once when all of a component's dependents get removed, in which the app unloads it from the registry, and again once all of its dependencies get removed, in which the app unloads it from the map
- So the only real important thing to keep note of is that the map has to keep track of two counts for each component: the amount of dependencies, and the amount of dependents. 
  - When the amount of dependents goes to zero, the map unloads it from the registry, but doesn't tell anyone.
  - When the amount of dependencies goes to zero, the map now reports it as unloaded and notifies people
  - If another component tries to get the unloading component while it's unloading, it'll have to wait until it finishes unloading
    - This could potentially lead to a deadlock, but that's better than being incorrect

## Static

- Recently switched to using static references for component IDs, but that's not fully sound D:
- From what I know, their strings will be stored in the rodata of the loaded dynamic libraries, which means that attempting to access them (potentially from the events list) after the library is unloaded should segfault
- But the switch was really really nice because it means that component ids could be cloned cheaply, which makes things way easier
- I see three solutions:
  - Stop unloading past dynamic libraries
    - This is what rubicon suggests
    - Would solve all my problems
    - Probably a very small performance penalty
      - Most users wouldn't be turning plugins on and off regularly
      - Only developers would, but the plugins should be small hopefully?
        - sautibara-rpc is 15.7mb, 100 revisions would take up 1.5gb, but maybe compression helps?
        - sautibara-ui is 76.8mb, which is way more...
    - May require keeping the old plugin dynamic library files alive
  - Send a "cleanup" event through the method and events queues
    - First through methods, then events
    - Simply just keeps the dynamic library alive until all events are viewed
      - Ensures that all component ids would be unloaded before unloading the library
    - Much much more flaky
      - Doesn't work if some other component decides to hold onto a component id for a while
    - Also removes the need of transient dependencies (as explained above), and they suck
  - Mixture of the two
    - Keep cleanup for correctness
    - Keep only the past few libraries alive, like ~5
    - Unlikely that there will be issues, but still possible
    - Probably have no unload for most users, and cleanup only for devs
    - Include some library cache in the arena so that turning on and off a plugin doesn't reload it
- Think I'll choose the mixture

## Lazy Resources

- Some dependencies shouldn't keep components loaded, but should keep them added
  - Examples
    - The owned app self-dependency
    - App's dependencies on some resources (resource-like resources, like Library)
  - This mirrors how dependencies work for the dependents
    - Keeps them added, but not loaded
  - We could call this a weak dependency, and normal dependencies as strong dependencies
    - Weak dependencies may load a resource, but they don't keep it around
      - They are required to be removed when the app calls unload, though
- This paves a bit of the ground for how resources should initially be run
  - Keep an on-load method for loaders, with an app with the app as a dependent
  - Non-lazy resources (see below) immediately get themselves and spawn their runner
  - Then, when a resource is unloaded, the loaded sends a message to the resource to stop it
    - Note that the loaded doesn't await any join handle, since that may cause a deadlock because this unload will be done with an owned app
- Resources should have the ability to determine themselves as lazy
  - Non-runnables will always be lazy, listeners will sometimes be lazy (Library would, Ui wouldn't)
  - It means:
    - The resource's runner won't start automatically on add
    - The resource's runner will instead start on load
    - The resource's runner won't keep the resource alive - it'll be a weak dependency instead

## Unloading / Removing

- How can we unload / remove a component on demand?
  - Get the state of the map and an event listener, compute the actions necessary, wait for things to get done
    - Fairly simple
    - Doesn't really work when the app changes - that is, if some component gains dependencies before getting removed
  - Make the app have the responsibility
    - Keep a map of all pending state changes w/ any listeners
      - Listeners are waiting for a state change to happen
    - State changes would be:
      - Components
        - Deactivating (Active -> Loaded)
        - Unloading (Loaded -> Added)
        - Removing (Added -> Removed)
      - Dependencies
        - Removing
    - Listeners would be simple:
      - Either the id of a different state change, who's getting blocked by a different one
      - Or a oneshot for a component that's waiting for the state change
    - When things change in the map, the map just has to look at the state changes affected
    - Listeners should be categorized into passive / active
      - Passive is just waiting for state changes
      - Active wants the state change to happen
        - Turning a state change active will turn all of its descendant listeners active, according to unloading rules
      - Actually this is a property of the state changes, not their listeners
  - How will this be stored?
    - Immutable HashMap of State Changes -> Metadata
    - Metadata would store who's listening to it
      - Necessary for when the state change actually happens to notify them
    - And also who it's listening for
      - Necessary for if it becomes active
    - State changes have to be tiny and easily cloneable, which is easy to do
